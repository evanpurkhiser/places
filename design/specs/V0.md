# V0 - Ingest, Store, Display

## Scope

V0 proves the end-to-end pipeline:

- add a place via API using Google Place ID
- store it idempotently in DB
- fetch/cache selected Google Place metadata
- render saved places on a map

## Definition of Done

- `POST /places` accepts a Google Place ID plus optional tags and creates one canonical place record.
- Re-adding the same Google Place ID returns `409 Conflict` and does not create duplicates.
- Place metadata is fetched from Google Places API; persistence follows the
  [metadata and retention design](../place-metadata.md).
- Google sync runs inline as part of `POST /places`; if sync fails, the request fails.
- Saved places are readable via a basic list API for UI/agents.
- Map view renders persisted places from DB-backed data.
- Local run flow is documented and repeatable (`add -> store -> render`).

## API Contract (V0)

### `POST /places`

Request body:

- `google_place_id` (required)
- `tags` (optional array of strings)

Behavior:

- Source capture and attachment follow the [source design](../sources.md);
  the request contract for these operations remains open.
- Tag normalization: trim whitespace, lowercase, de-duplicate.
- Namespaced tags are convention, not requirement. Current conventions include:
  - `source:*`
  - `country:*`
  - `city:*`
  - `type:*`
- If `google_place_id` already exists, return `409 Conflict`.
- Google metadata sync runs during the request.
- If sync fails, the request fails (no partial success).
- Error responses can be minimal in V0. Use `400` with a `details` key for failure context.

### `GET /places`

Simple list response is sufficient for V0 map rendering and agent reads.

Response should include at least:

- `google_place_id`
- `name`
- `lat`
- `lng`
- `tags` (resolved from relational tag tables)

Pagination/sorting can remain minimal in V0 and be expanded later.

Default ordering for `GET /places` is `created_at DESC`.

## V0 Data Contract

The selected initial metadata fields are `name`, `formatted_address`,
`google_maps_url`, and `coordinates` (a PostGIS geographic point). Additional
provider fields below are future candidates subject to the
[metadata and retention design](../place-metadata.md). Persistence and raw-response
retention require a field-specific policy before implementation.

### Stored Fields (Application-Level)

- `google_place_id` (required, unique)
- `name`
- `formatted_address`
- `lat`
- `lng`
- `google_primary_type`
- `google_types` (array)
- `timezone` (IANA)
- `user_note` (optional)
- `last_sync_at` (timestamp of last successful Google sync)
- `google_place_raw_json` (candidate response snapshot, subject to permitted retention)
- `created_at`
- `updated_at`

A permitted response snapshot contains only the requested fields and follows the
same retention policy as its derived columns.

### Source Storage

Store discovery context in dedicated source records as described in
[Sources](../sources.md). The place/source relationship and ingestion-mechanism
tracking remain open decisions.

### Tag Storage

Use relational tag tables for V0:

- `tags`
  - `id` (primary key)
  - `name` (unique, normalized: trimmed, lowercase)

- `place_tags`
  - `place_id` (foreign key to `places.id`)
  - `tag_id` (foreign key to `tags.id`)
  - unique constraint on (`place_id`, `tag_id`)
  - optional `created_at`

`POST /places` tag behavior:

- normalize tags (trim, lowercase, de-duplicate)
- upsert normalized tag names into `tags`
- attach mappings in `place_tags`
- if place already exists (`409`), do not mutate tags

### Hours Storage

Store hours in two forms:

- `hours_json`: raw opening-hours payload from Google.
- `hours_intervals`: normalized intervals for efficient future querying.

`hours_intervals` is a separate table (`place_open_intervals`), not an embedded field on `places`.

Suggested `place_open_intervals` columns:

- `google_place_id` (or internal `place_id` foreign key)
- `day_of_week` (`0-6`)
- `open_minute` (`0-1439`)
- `close_minute` (`1-1440`)
- `interval_type` (start with `regular`; expand later)
- `source` (for example `regularOpeningHours`)
- `updated_at`

Normalization requirements:

- support multiple windows per day (e.g. `08:00-14:00`, `17:00-22:00`)
- support overnight windows by splitting across days (e.g. `17:00-02:00`)
- preserve timezone correctness via place timezone

Indexing direction (for future filtering performance):

- index on `day_of_week`
- index on (`day_of_week`, `open_minute`, `close_minute`)

## Google Places API Notes

V0 should use explicit field selection for current product needs. See the
[metadata proposal](../place-metadata.md) for field priorities, billing tiers, and
storage constraints.

Relevant Place fields include:

- `id` / resource `name`
- `displayName`
- `formattedAddress`
- `location`
- `types`
- `primaryType`
- `regularOpeningHours`
- `timeZone`

Additional fields require an expanded field mask and a retrieval/retention policy.
