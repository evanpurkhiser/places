# V0 - Ingest, Store, Display

## Implemented scope

V0 connects Google Maps inputs, queued metadata fetching, PostgreSQL storage,
API/CLI listing, and a web map of saved places. Place identity is an internal UUID;
Google Place IDs are unique provider identifiers. Reimporting an existing place
reuses it and applies supplied annotations.

## API and CLI contracts

The server exposes oRPC at `/rpc`. Shared inputs, outputs, and errors are defined
in `packages/common/src/contract`; the root README documents the CLI commands.

| RPC                                | Purpose                                                    | CLI                                 |
| ---------------------------------- | ---------------------------------------------------------- | ----------------------------------- |
| `places.import`                    | Resolve a Maps link or `gmaps:<place_id>` and queue import | `places import`                     |
| `places.importStatus`              | Read job state and resulting place IDs                     | `places import-status`              |
| `places.list`                      | Return saved places matching an optional query             | `places list --query`               |
| `places.tag`, `places.untag`       | Manage tag assignments and assignment notes                | `places tag`, `places untag`        |
| `places.sync`, `places.syncStatus` | Queue and inspect metadata refreshes                       | `places sync`, `places sync-status` |
| `places.searchGoogle`              | Return Google Text Search candidates                       | `places search-gmaps`               |
| `tags.*`                           | Create, list, get, rename/update, and delete tags          | `places tags`                       |
| `query.describe`                   | Describe registered search capabilities                    | `places docs filter`                |

Import accepts an input string, existing tag names/IDs with optional assignment
notes, and an optional general place note. Unknown tags fail before enqueueing.
Omitted notes preserve existing annotations; supplied empty notes clear them.
Tags are normalized and deduplicated, while note text is preserved.

The worker fetches and validates metadata before completing an atomic place/tag
write. Failed imports leave no partial place and retry through pg-boss. The API
returns a job ID immediately; status reports completion or failure. Completed job
status is retained for seven days.

Listing returns all matches, ordered by `createdAt` and ID descending, including
named coordinates and complete tag associations. Pagination and selectable
ordering are future work. Query failures have structured source-located diagnostics.

## Stored data

`places` stores the internal UUID, unique Google Place ID, name, formatted address,
Maps URL, PostGIS point, IANA time zone, business status, weekly hours, user note,
last successful sync time, and creation/update timestamps. See
[place metadata](../place-metadata.md) for field names and ownership.

`tags` have normalized unique names, optional icon/description, and timestamps.
`place_tags` uses a composite place/tag key and stores an optional assignment note.
Tag deletion removes assignments while preserving places.

`sources` and `place_sources` provide a many-to-many discovery-context schema.
Source APIs and capture pipelines remain planned; see [sources](../sources.md).

## Geographic and hours representation

Coordinates use `geography(Point, 4326)` with a GiST index. The API derives
`{latitude, longitude}` from that point.

Opening hours use a nullable `int4multirange` on `places`, with a GiST index and
bounds check. Components are inclusive-start/exclusive-end offsets in a Sunday-first
local week. Normalization merges adjacent/overlapping periods and splits week
boundaries. Unknown hours are null; an empty range set means closed all week.
See [hours](../hours.md) and [time values](../time-values.md).

## Web and operations

The React/Vite web package combines the user's query with map-bound rectangles,
displays pins and a result list, and shows saved-place details. Web capture and
editing are planned. The root README documents API/worker configuration, migrations,
local development, container operation, and checks.
